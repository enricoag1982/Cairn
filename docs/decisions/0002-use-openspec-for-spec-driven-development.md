# Use OpenSpec for spec-driven development

## Context and Problem Statement

Requirements in this project will change often. AI coding agents do much of the implementation, and they work best from explicit, current, testable requirements.
We need one place that states what the system must do *now*, and a reviewable way to change it that keeps the history of *why* it changed.

## Decision Drivers

- A single, always-current statement of required behavior, not a pile of per-feature documents
- Changes reviewable as diffs before any code is written
- Works on a growing codebase, not only a new one
- Plain Markdown in git, validated in CI
- Supported by many AI coding tools, not locked to one IDE or vendor

## Considered Options

- [OpenSpec](https://github.com/Fission-AI/OpenSpec)
- [GitHub Spec Kit](https://github.com/github/spec-kit)
- [Kiro](https://kiro.dev/) specs
- BMAD Method
- Plain Markdown requirement documents without tooling

## Decision Outcome

Chosen option: "OpenSpec", because it keeps a merged, current spec per capability (`openspec/specs/`) and expresses every change as a delta (`ADDED`/`MODIFIED`/`REMOVED`/`RENAMED` requirements).
Archived changes keep the dated proposal, design and tasks, and the CLI validates everything strictly in CI.

The CLI version is pinned in `package.json` (`@fission-ai/openspec`). Agent integrations are generated by `openspec init`/`openspec update` for Claude Code and for the shared `.agents/skills/` folder.
Add more tools with `npx openspec init --tools <list>`.

### Consequences

- Good, because `openspec/specs/` always shows the current contract, and agents can read it with `openspec show`.
- Good, because the change and archive folders record the history of behavior, next to ADRs for the history of reasoning.
- Good, because it has no runtime footprint: Markdown plus a Node.js CLI used only for tooling.
- Bad, because OpenSpec's agent integration layer has changed often (1.x moved from `AGENTS.md` blocks to generated skills). Pinning the version and regenerating with `npm run agents:update` contains this.
- Bad, because `MODIFIED` deltas must repeat the whole requirement, and headers must match exactly. `openspec/CLAUDE.md` warns agents about this.
- Neutral, because OpenSpec has no project-wide decision log or "constitution". ADRs ([ADR-0001](0001-record-architecture-decisions-with-madr.md)) and [principles](../principles.md) cover that.

### Confirmation

`npm run specs:validate` (`openspec validate --all --strict`) and `openspec validate --archived` run in CI on every pull request.

## Pros and Cons of the Options

### OpenSpec

- Good, because specs are anchored to the code: merged current specs plus delta changes suit long-lived, evolving systems.
- Good, because the format is lightweight (Markdown, SHALL/MUST requirements, WHEN/THEN scenarios) and the validator is strict.
- Good, because it supports many tools (Claude Code, Codex, Copilot, Cursor, Gemini CLI and others).
- Bad, because the integration layer is young and moves fast.

### GitHub Spec Kit

- Good, because of its "constitution" concept and its quality gates (clarify, analyze, checklist).
- Bad, because specs are per feature (`specs/NNN-feature/`) with no merged current truth, so drift is left to the team.
- Bad, because it generates more artifacts per feature and needs Python tooling.

### Kiro specs

- Good, because EARS-style acceptance criteria are precise and testable.
- Bad, because specs are per feature and the workflow is tied to the Kiro IDE and CLI.

### BMAD Method

- Good, because of rich role-based planning (analyst, PM, architect) for large new projects.
- Bad, because it is heavy, not delta-based, and has a large runtime folder in the repository.

### Plain Markdown documents

- Good, because there is no tooling.
- Bad, because there is no enforced structure and no validation, and "current" and "proposed" behavior are easily confused.
